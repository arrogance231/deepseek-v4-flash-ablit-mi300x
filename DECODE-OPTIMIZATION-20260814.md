# Decode optimization round 2 (2026-08-13–14)

## Result

This round profiled the target model without speculative decoding at fixed
`M=16/32/64`, optimized only exact or demonstrably equivalent operations, then
restored the production static DSpark K=7 configuration. The 2× stretch target
was not reached. The retained changes removed 508 GPU operations and 4.858 ms
from the representative M64 graph, while improving native request throughput by
9–11%.

| Native batch | Baseline aggregate | Final aggregate | Baseline per-user | Final per-user |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 595.31 tok/s | 662.29 tok/s (+11.3%) | 40.04 tok/s | 44.63 tok/s (+11.5%) |
| 32 | 995.63 tok/s | 1,096.19 tok/s (+10.1%) | 34.10 tok/s | 37.69 tok/s (+10.5%) |
| 64 | 1,489.14 tok/s | 1,624.19 tok/s (+9.1%) | 26.41 tok/s | 29.12 tok/s (+10.3%) |

The fixed M64 graph fell from **32.620 ms / 2,439 operations** to
**27.763 ms / 1,931 operations**: **-14.9% / -508 operations**. Request-level
throughput improves less because it includes prompt work, graph ramp-up, request
completion skew, scheduling, and sampling.

## Measurement method

The native baseline disabled DSpark and used five 256-token runs at each of
M16, M32, and M64. Prompts, seeds, sampling, and output lengths were fixed. These
batches approximate the target verification work generated by static K=7 at
production C2, C4, and C8.

For profiling, only the steady annotation named
`execute_M_context_0...generation_M` was selected. Prompt graphs, Python
wrappers, allocator activity outside the annotation, and overlapping outer
annotations were excluded. The median-duration graph was categorized. The
model has **43 MoE layers** in this graph; using 48 overstates projected savings.

## Retained changes

### 1. Exact shared-expert SwiGLU/clamp fusion

The shared expert activation previously launched seven BF16 elementwise
operations per layer. `swiglu_clamp.hip` performs them in one launch while
explicitly reproducing every BF16 round-to-nearest-even boundary. It is not the
usual algebraically fused FP32 expression.

Validation covered all finite BF16 scalar inputs at the sensitive boundaries
and one million random pairs; outputs were bit-identical. Together with schedule
reuse below, the first integrated support candidate reduced M64 from 32.620 ms
and 2,439 operations to 30.498 ms and 2,138 operations.

### 2. Reuse the routing-created BM16 schedule

`_fast_deepseek_routing` already constructs block schedules for the supported
tile sizes. The custom native M<=64 MoE path nevertheless rebuilt BM16 in a
second `schedule_kernel<16>` launch. It now consumes
`routing.expt_data.block_schedule(16)` directly; larger prefill shapes retain
the custom BM48/BM64 schedule.

The reused schedule, W1 output, W2 output, and final MoE output were
bit-identical. This removes all 43 redundant schedule launches, about
0.22 ms/graph.

### 3. Copy only active block-table columns

Five block tables were copied at their 393,216-token maximum width every decode
step, even for short requests. Allocation and GPU row stride remain unchanged,
but `commit_block_table` now transfers only columns through the maximum active
row width.

At M64 the five transfers changed from 0.785 ms and 40.9 MB per graph to
0.024 ms and 51.5 KB. Tests retained the full destination stride, checked the
valid prefix exactly, verified untouched tail sentinels, and covered zero-width
rows and block sizes 256/64/8/4. The final near-limit 393,051-total-token recall
gate is the decisive integrated validation.

### 4. Keep router logits in BF16

The router GEMM already produced BF16 values. `GateLinear` converted them to
FP32, after which the top-k kernel converted each value back to BF16. Declaring
the gate output BF16 removes 43 conversions (0.211 ms) without changing the
values entering top-k.

Learned and hash routing at M8/16/32/64 produced bit-identical expert IDs and
weights.

### 5. Remove sparse-attention support copies and general-purpose sorting

The sparse decode reduction now writes into vLLM's supplied output tensor,
instead of allocating an output and copying it afterward. The selected 512
indices are canonicalized by one fixed-width Triton sort per row rather than
PyTorch radix sort, `arange`, and copy-buffer helpers.

The supplied-output and allocation paths were bit-identical on real packed FP8
DS-MLA cache fixtures. Sort tests covered 1/8/16/32/64/448 rows, duplicates,
`-1`, `INT_MIN`, and `INT_MAX`; every result matched descending PyTorch sort.

This removed 106 `copyBuffer` calls (0.530 ms), 21 radix sorts (0.345 ms), and
21 `arange` calls (0.097 ms), replacing them with 21 fixed sorts (0.139 ms).

### 6. Fold sparse-logit NaN handling into stable top-k

The stable HIP top-k extension now applies the exact
`nan_to_num(nan=-inf)` ordering transform while loading logits:

- NaN becomes negative infinity;
- positive infinity becomes `FLT_MAX`;
- negative infinity becomes `-FLT_MAX`.

That removes 21 standalone `nan_to_num` launches (0.377 ms). Tests compared
the old MQA-output + sanitize + top-k chain with original MQA output + new
top-k. Actual MQA indices and finite stress cases were exact. The source is
`patches/sampler.topk-tiebreak-sanitize.cu`; `prepare-artifacts.sh` expands the
validated binary.

## Rejected or exhausted work

### Persistent/grouped W1 and W2

The current path already groups all routed experts into one W1 and one W2
launch, uses direct global-to-LDS loads, and avoids per-expert launches. An M64
routing capture activates roughly 195 experts. A cold expert sweep requires
about 2.49 GiB of compressed W1+W2 weights per layer; the measured cold
first-layer time was about 0.50 ms, near the MI300X HBM-bandwidth floor.

The W1-to-W2 intermediate is only about 1.5 MB, so eliminating it cannot offset
the expert-weight traffic. A truly persistent fusion also needs cross-workgroup
coordination because W2 consumes the complete 2,048-wide W1 result. It is not a
credible large exact win without changing weight format, arithmetic, or model
routing.

### MHC cross-op fusion

A fused MHC prototype explicitly inserted the model's BF16 boundary. Residual
and layer input were exact, but recurrent FP32 `post_mix`/`comb_mix` state still
drifted by up to roughly `5.96e-8`. The projected whole-graph saving was only
about 0.34 ms. Recurrent state amplifies even tiny changes across layers, so the
prototype was rejected.

### Alternative MoE geometries and arithmetic

- W1 NF2 was exact and 14.6% faster at M8, but 2.3% slower at M64.
- The W2 NF2 prototype was incorrect and caused an offline GPU memory fault.
- Reassociated W2 accumulators were faster but changed deterministic model
  fixture continuations, despite small relative-L2 error.
- INT8/FP8 W2-intermediate variants either drifted or did not beat the direct
  FP16/BF16 path enough to justify promotion.
- Fusing input quantization into expert tiles duplicates work across
  expert/output tiles to save only about 8–10 microseconds per layer.

### Sanitize in the MQA writer

Sanitizing NaNs in the Gluon MQA output store cut its isolated time from about
104 to 52 microseconds, but altered 1,709 finite logits by up to `1.9e-6`
because it changed generated code. This was rejected. Folding the same semantic
operation into top-k retained the original MQA binary and exact finite logits.

### Dense GEMM tables and remaining small fusions

Prior dense-table rows won 7–52% in isolated operators but only tenths of a
millisecond end to end. Standalone tuning is exhausted; useful future work must
absorb norm/quant/residual work into an exact epilogue. Top-k + routing fusion,
input-quant overlap, and routed/shared-output merging each have only about
0.2–0.3 ms expected upside and cross stable vLLM API or stream boundaries.

## Why 2× was not achieved

Doubling the original M64 request throughput requires 2,978 tok/s. Even a
perfectly occupied 27.763 ms graph emits at most about 2,305 target tokens/s at
M64 before request ramp-up and scheduler overhead. A 2× result therefore needs
a graph below 21.5 ms plus lower host/request overhead—another 6.3 ms beyond
this round.

The final graph still spends 10.60 ms in W1+W2, 6.26 ms in dense GEMMs, and
3.82 ms in sparse attention. MoE is primarily compressed-weight bandwidth;
dense kernels were already extensively swept; MHC exact fusion failed its
recurrent-state gate. Further gains remain possible, but 2× now requires a
model-level weight/arithmetic change or a major cross-layer execution design,
not another launch/configuration sweep.

## Final production gates

The checked-in `compose.yaml` retains static DSpark K=7, the 384-slot draft
reservation, `max_num_batched_tokens=4096`, `max_num_seqs=64`, and
`max_model_len=393216`.

- Health: inference and Caddy remained healthy after the final start.
- Tools: 16/16 two-turn structured tool-call fixtures passed.
- Prefill: seven uncached C1 runs were 11,617–11,674 tok/s; median
  **11,657 tok/s** (no regression from 11,487).
- Mixed load, three uncached seeds: median 50K-prefill TTFT **7.129 s**,
  late-short TTFT **296 ms**, and maximum background decode gap **164 ms**.
- Long context, cold: 379,006 prompt tokens recalled all three needles with the
  same output SHA-256 as the prior production build in **51.077 s**.
- Long context, warm: 378,880 cached tokens, exact recall and the same hash in
  **1.314 s**.
- Near limit: a request with 393,010 prompt and 393,051 total tokens recalled
  all three needles exactly, leaving 165 tokens below the configured limit.
- Capacity: C64 completed at 1,260 tok/s aggregate and 24.84 tok/s/user.

A legacy untemplated `/v1/completions` recall prompt emitted filler in one
379,998-token diagnostic. The production `/v1/chat/completions` gate passed
cold, warm, and at 393,051 total tokens; the raw prompt is therefore not treated
as a model-quality guarantee.

Raw measurements and traces remain on the host under
`/opt/deepseek-v4/optimization-20260813-decode-round2/`. The production source,
binary artifact, hashes, and mount list are preserved in this repository.
